# Phase 1 — UI Design Contract

> Visual and interaction contract for the Foundation phase's only UI surface: the System Health landing page. Generated by gsd-ui-researcher, verified by gsd-ui-checker. This document also establishes baseline visual conventions (color roles, spacing scale, typography scale, icon system) that Phases 2-5 inherit — later UI-SPECs should extend, not contradict, this one.

---

## Design System

| Property | Value |
|----------|-------|
| Tool | none — Streamlit is not React/Next.js/Vite; no `components.json`, no shadcn. Confirmed via repo scan: greenfield, only `CLAUDE.md`/`apollo.MD`/`spec.MD`/`.planning/` exist at repo root. |
| Preset | not applicable |
| Component library | none — Streamlit 1.59+ native widgets only: `st.status`, `st.metric`, `st.error`/`st.warning`/`st.success`, `st.badge`, `st.container(border=True)`, `st.columns`, `st.button`, `st.checkbox`. Zero custom component packages, zero custom CSS frameworks, per CLAUDE.md ("Zero JavaScript... Streamlit covers 100% of UI needs"). |
| Icon library | Streamlit's built-in Material Symbols shorthand (`:material/icon_name:`), usable inside `st.badge`, `st.button`, and markdown text. No external icon package. See icon assignments below. |
| Font | Streamlit's default theme font stack ("sans serif" — system UI font, no custom `@font-face`). Base size 16px. Set explicitly in `.streamlit/config.toml` rather than left to whatever ships by default, so later phases inherit the same values instead of theme drift. |

**`.streamlit/config.toml` theme block to create in this phase** (declares the values used throughout this document):

```toml
[theme]
primaryColor = "#2563EB"
backgroundColor = "#FFFFFF"
secondaryBackgroundColor = "#F0F2F6"
textColor = "#0F172A"
font = "sans serif"
baseFontSize = 16
headingFontWeights = 600
```

`primaryColor` is deliberately set to blue (#2563EB), not Streamlit's default red (#FF4B4B) — the default primary color collides visually with `st.error`'s built-in red, which would make a plain accent button look like a failure state. `headingFontWeights = 600` is set uniformly across h1–h6 so the two-weight typography contract below holds exactly (Streamlit's un-configured default varies h1 vs. h2–h6).

## Spacing Scale

Declared values (multiples of 4), mapped to Streamlit's native layout primitives (no custom CSS injection):

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Gap between a status icon and its label text inside a badge (e.g. `:material/check_circle:` + "Apollo: OK") |
| sm | 8px | Gap between the three health-check icons/badges when shown inline in a summary row |
| md | 16px | Default gap between stacked `st.container(border=True)` health-check cards; `st.columns(gap="small")` |
| lg | 24px | Internal padding within each `st.container(border=True)` health-check card (Streamlit's default bordered-container padding) |
| xl | 32px | Gap between major page sections: page header block → health-check cards → any footer/help text |
| 2xl | 48px | Space above `st.title("System Health")` and below the last section on the page |
| 3xl | 64px | Reserved, not used on this single-section Phase 1 page — available for later phases' multi-section dashboards (e.g. Phase 5 Analytics) |

Exceptions:
- `st.columns(gap=...)` and `st.container(border=True)` only accept keyword gap sizes (`small`/`medium`/`large`), not arbitrary pixel values — treat the px values above as target rendered spacing achieved through Streamlit's own defaults and component choice, not enforced CSS. Do not introduce custom CSS injection to force pixel-exact spacing in this phase.
- Touch targets: the "Recheck Connection" button and the DKIM self-attestation checkbox must not be visually shrunk below Streamlit's default control height (~40px) — treat 44px as the floor if any future custom styling is considered.

## Typography

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 16px | 400 (regular) | 1.5 |
| Label / Caption | 14px | 400 (regular) | 1.5 |
| Heading | 24px | 600 (semibold) | 1.2 |
| Display | 36px | 600 (semibold) | 1.2 |

Mapping to Streamlit components:
- Display (36px/600) → `st.title("System Health")` — the single page title.
- Heading (24px/600) → `st.header(...)` for each of the three check sections: "Apollo Connection", "Apollo Credits", "Mailbox Deliverability".
- Body (16px/400) → default markdown/`st.write` text, banner/status messages.
- Label/Caption (14px/400) → `st.caption(...)` for helper/next-step text under banners (e.g. the exact remediation sentence under a failed check).

Only two weights are used across the whole page (400 and 600) — enforced via the `headingFontWeights = 600` theme override above, so `st.header`/`st.subheader`/`st.title` render consistently rather than Streamlit's un-configured per-level variance.

## Color

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | #FFFFFF | Page background, main content area |
| Secondary (30%) | #F0F2F6 | `st.container(border=True)` card backgrounds for each health-check block; any sidebar surface added in later phases |
| Accent (10%) | #2563EB | Reserved exclusively for: the "Recheck Connection" button, and (in later phases) the active/selected item in `st.navigation`'s sidebar nav. Never used for status semantics. |
| Destructive | #DC2626 | Reserved for destructive actions only — none exist in Phase 1 (see Copywriting Contract). First use is Phase 4's bulk-enrollment approval flow. |

Accent reserved for: the primary "Recheck Connection" CTA button, and the active-page highlight in the sidebar nav introduced by later phases. Not used anywhere in the pass/fail/unknown status system below — those use Streamlit's own semantic colors so status meaning is never confused with brand/accent meaning.

**Status semantic colors** (Streamlit's built-in notification colors, not custom-defined — deliberately kept separate from `primaryColor`/accent):

| State | Color | Streamlit primitive |
|-------|-------|----------------------|
| Pass | green (~#21C354) | `st.success`, or `st.status(..., state="complete")` |
| Fail / hard-blocked | red (~#FF4B4B) | `st.error`, or `st.status(..., state="error")` |
| Unknown / degraded | amber (~#FFA421) | `st.warning` |
| Informational (never blocks) | neutral gray/slate, no red/green/amber tint | `st.metric` (no colored delta), not `st.success`/`st.error` |

## Health Check State System

This is the core interaction contract for Phase 1 — the executor should treat this table as authoritative for how each of the three checks renders and gates.

| Check | States | Blocking Behavior | Visual Treatment |
|-------|--------|--------------------|--------------------|
| Apollo API key validity | Pass / Fail | **Hard block (D-01).** On Fail, render only this check's failure banner + "App blocked" message, then `st.stop()` — no other section of the page renders, because nothing downstream is usable until this passes. | Pass: green `st.status`/`st.success`, icon `:material/check_circle:`. Fail: red `st.status(state="error")`/`st.error`, icon `:material/cancel:`. Fail must visually dominate the page (full-width banner, not a small badge) since it is the one state that stops everything. |
| Apollo credit balance | Informational only (no pass/fail states) | **Never blocks (D-03).** | Rendered via `st.metric(label="Apollo Credits Remaining", value=N)` — neutral, no red/green coloring, visually lower-stakes than the Apollo key check above (smaller footprint, no full-width banner, no icon badge). If unavailable, show muted caption text "Credit balance unavailable — this won't stop you from using the app," never an error-colored banner. |
| Mailbox deliverability — SPF | Pass / Fail | **Soft block (D-02)** — affects only the future send/enroll step (not built until Phase 4); Phase 1 renders the state but gates nothing yet. | Pass: green, icon `:material/check_circle:`. Fail: amber `st.warning` (not red — this never hard-blocks anything in this phase, so it should not visually read as identical-severity to the Apollo hard-block), icon `:material/error:`. |
| Mailbox deliverability — DMARC | Pass / Fail | Soft block (D-02), same as SPF. | Same visual treatment as SPF. |
| Mailbox deliverability — DKIM | Pass / **Unknown** (third state — never a hard Fail per RESEARCH.md Pitfall 2) | Soft block (D-02); "Unknown" is treated as non-blocking, same severity as attested-pass. | Pass: green, icon `:material/check_circle:`. Unknown: amber `st.warning`, icon `:material/help:` — visually distinct from both Pass (green) and a hypothetical Fail (red is never used for DKIM). Paired with a self-attestation `st.checkbox("I've configured DKIM for this domain")` shown only when the state is Unknown. |

Icon assignments (Material Symbols shorthand, used consistently across all phases):
- Pass → `:material/check_circle:`
- Fail (hard block only — Apollo key) → `:material/cancel:`
- Soft-fail (SPF/DMARC not found) → `:material/error:`
- Unknown (DKIM undetectable) → `:material/help:`
- Informational / non-blocking metric → `:material/toll:`
- Manual recheck action → `:material/refresh:`

## Copywriting Contract

| Element | Copy |
|---------|------|
| Page title | "System Health" |
| Page subtitle (caption under title) | "Checked automatically every time the app loads." |
| Primary CTA | "Recheck Connection" — `st.button("Recheck Connection", icon=":material/refresh:")`, re-runs all three checks in place without requiring a full app restart. Placed directly below the Apollo Connection card. |
| Apollo Fail banner — missing/invalid key (401) | "Apollo connection failed — check that APOLLO_API_KEY is set correctly in Streamlit secrets." (exact wording locked by CONTEXT.md) |
| Apollo Fail banner — wrong key type (403) | "Apollo connection failed — this key is not a Master API key. Check Apollo Settings → Integrations → API Keys." |
| Apollo Fail banner — network/unexpected error | "Apollo connection failed — check your internet connection and try again." |
| App-blocked explanation (shown alongside any Apollo Fail state) | "The rest of the app is unavailable until this is fixed. Fix the issue above, then click Recheck Connection." |
| Credit balance unavailable | "Credit balance unavailable — this won't stop you from using the app." |
| SPF fail | "SPF: not found — add a TXT record starting with v=spf1 to your sending domain's DNS settings before sending a campaign." |
| DMARC fail | "DMARC: not found — add a TXT record starting with v=DMARC1 at _dmarc.<your-domain> before sending a campaign." |
| DKIM unknown | "DKIM: could not auto-detect. This doesn't necessarily mean it's misconfigured — some providers use custom selectors. If you've already set up DKIM with your email provider, check the box below to confirm." |
| DKIM self-attestation checkbox | "I've configured DKIM for this domain" |
| Mailbox section framing (caption under "Mailbox Deliverability" heading) | "These checks won't stop you from using the app today, but a campaign can't be sent until they pass (or DKIM is manually confirmed)." |
| Loading / pre-check state (transient, shown while checks run — closest Phase 1 analog to an "empty state," since no data lists exist yet) | `st.spinner("Checking Apollo connection and mailbox setup...")` — no separate empty-state copy needed; this phase has no list/table views. First true empty-state copy arrives in Phase 2 (empty contact list) and Phase 4 (empty review queue). |
| Destructive confirmation | None in Phase 1 — no destructive actions exist on the health page (no delete/clear/reset controls). The first destructive action (bulk sequence enrollment approval) arrives in Phase 4; its confirmation copy and pattern will be defined in that phase's UI-SPEC. |
