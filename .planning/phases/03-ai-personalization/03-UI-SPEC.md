# Phase 3 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope note:** This phase extends `pages/discovery_page.py` (no new page). It adds three UI elements after the existing "Enrichment complete" success banner: (1) a progress indicator during the personalization loop, (2) a per-contact "View draft" expander, (3) a conditional batch-failure warning banner. No new buttons, no new pages, no new color tokens. Design system detection: this is a Python/Streamlit app (CLAUDE.md explicitly excludes React/Next.js/Vue) — **the shadcn gate does not apply**.

## Interaction Contract (Phase-Specific)

### 1. Progress indicator during the personalization loop

- **Component:** `st.progress(value, text=...)`, held in a placeholder (`st.empty()`) so it can be cleared after the loop completes — mirrors the self-clearing behavior of this page's existing `st.spinner(...)` blocks (Discovery's Find/Enrich stages).
- **Trigger:** Starts immediately after `insert_enriched()` succeeds inside the existing "Enrich & Continue" handler (D-01) — no separate button.
- **Exact copy (locked):** `"Personalizing drafts... {i}/{total}"` — starts at `"Personalizing drafts... 0/{total}"` before the first iteration, updates after each contact completes (success OR fallback both count as "done" for progress purposes — the counter reflects contacts processed, not contacts successfully AI-personalized).
- **Behavior:** Runs synchronously (sequential loop per RESEARCH.md's recommendation — no async/concurrency this phase). Bar fill uses the theme's `primaryColor` automatically (Streamlit default — no override needed).
- **Completion:** Placeholder is cleared (`.empty()`) once the loop finishes, immediately followed by the (conditional) D-16 warning banner and then the results section — matches the existing pattern where `st.spinner` blocks disappear once their operation completes.

### 2. Per-contact "View draft" expander

- **Placement:** Rendered **after** the existing `st.dataframe` (Name/Company/Title/Email — unchanged from Phase 2), separated by one `st.divider()`, under a new `st.subheader("Email Drafts", icon=":material/drafts:")`.
- **Structure:** One `st.expander` per contact, in the **same order** as the rows in the `st.dataframe` above it, so row N in the table visually corresponds to expander N below it (no separate sort/filter — this is a lightweight bridge, not the formal Phase 4 Review Queue).
- **Expander label (locked):** `"View draft — {Name} ({Company})"` — e.g., `"View draft — Jamie Chen (Acme Corp)"`. Icon: `icon=":material/mail:"`.
- **Default state:** Collapsed (`expanded=False`) for every row. With up to 50 contacts, all-expanded-by-default would produce an unusably long page.
- **Draft preview block (D-03 — single combined block, not split into "AI part" vs "template part"):**
  Rendered as a single `st.code(full_text, language=None)` call inside the expander, where `full_text` is:
  ```
  Subject: {subject}

  {body}
  ```
  Subject and body are visually one continuous monospace block (matches "as it would actually be sent" per D-03) — no separate widget, no separate styling, no bold/color-highlighting of the AI-generated opening line versus the template sentences around it. `st.code` also gives the teammate a free copy-to-clipboard affordance, useful since Phase 3 has no edit capability (that's out of scope — Phase 4 territory).
- **No caption/metadata row is added below the code block** (see item 4 below for the explicit reasoning).

### 3. Batch-failure warning banner (D-16)

- **Component:** `st.warning(...)` — **not** `st.error`. Rationale: this page's own established convention (see `pages/health_page.py`'s SPF/DMARC checks) uses `st.warning` for a degraded-but-non-blocking condition, and reserves `st.error` for a hard failure where the requested operation did not complete at all (e.g., this page's own "Contact enrichment failed" banners). A high fallback rate means drafts still exist and are still usable — degraded, not failed — so `st.warning` is correct, not `st.error`.
- **Icon (locked):** `icon=":material/error:"` — matches the existing `st.warning` icon convention already used for SPF/DMARC (`health_page.py`), not `:material/help:` (reserved for the DKIM "unconfirmed, needs manual check" case, which doesn't apply here).
- **Exact copy (locked, from CONTEXT.md D-16):** `"AI personalization is unavailable right now — drafts are using generic openers."`
- **Trigger condition:** `fallback_count / total > 0.5` (locked default per RESEARCH.md's explicit recommendation — a strict majority, matching D-16's "high fraction" framing; adjustable by the planner if execution reveals a better threshold, but `0.5` is the contract default).
- **Placement:** Immediately after the progress placeholder clears, **before** the `st.dataframe` and "Email Drafts" section — same position pattern as this page's existing error/success banners (rendered right after their triggering operation, before the results below).
- **Non-blocking:** Never calls `st.stop()`. Every contact still gets a full draft (D-14) and the table/expanders below render normally regardless of this banner's presence — matches this page's established "never hard-stop, keep inputs/results usable" rule.
- **Below-threshold behavior:** No banner, no per-row indicator — occasional individual fallback is silent by design (D-16 explicit).

### 4. AI-generated vs. fallback opening line — deliberate lack of visual distinction

**Locked decision: no visual distinction in the draft preview.** The assembled email in the `st.expander` renders identically whether the opening line came from Claude or the fallback template — no badge, no color tag, no "(AI)" / "(Standard)" label, no icon difference between rows.

Rationale (extends D-16's own stated philosophy): CONTEXT.md is explicit that below the failure threshold, "per-contact fallback is silent — no banner for occasional individual failures." Adding a per-row source tag would contradict that intent — it would surface exactly the individual-level signal D-16 deliberately chose to suppress, and it introduces a labeling question ("Standard opener" sounds like a downgrade) with no user-facing decision attached to it in this phase (there's no per-contact retry/edit action until Phase 4). The single aggregate warning banner (item 3) is the only signal surfaced to the teammate; individual rows are visually uniform. `draft_source` is still persisted per-row in SQLite (per RESEARCH.md's schema) for future use (e.g., a Phase 4 filter), but nothing in this phase's UI reads or displays it.

### 5. Spacing/layout of the new section within the existing results area

Order of elements after a successful "Enrich & Continue" (unchanged elements marked *existing*):

1. *(existing)* `st.success("Enrichment complete — N contacts ready.")`
2. **(new)** Progress placeholder — appears here, then clears itself
3. **(new, conditional)** `st.warning(...)` — D-16 banner, only if threshold exceeded
4. *(existing)* `st.dataframe(table_rows)` — Name/Company/Title/Email, unchanged
5. **(new)** `st.divider()`
6. **(new)** `st.subheader("Email Drafts", icon=":material/drafts:")`
7. **(new)** One `st.expander(...)` per contact, collapsed, in table row order

No custom margin/padding CSS — spacing between all of the above is native Streamlit block spacing, consistent with every other section on this page and on `health_page.py`.
