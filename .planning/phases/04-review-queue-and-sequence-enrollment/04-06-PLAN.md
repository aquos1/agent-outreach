<objective>
Make the AI opening line actually reach Apollo: resolve (or create) the custom field that carries it, and identify the contacts that `bulk_create` leaves unmodified so their opening line can be applied with a follow-up update.

Purpose: Without this, enrollment adds contacts to a sequence that sends a static template and Phase 3's personalization never leaves this app (D-14). This plan supplies the two pieces 04-04 wires into the approve flow. It runs after 04-03 because both extend `apollo/client.py` and `review/logic.py`.

</objective>

Apollo endpoints this plan adds (CITED, live docs.apollo.io fetch — 04-RESEARCH.md §1):
  GET   {APOLLO_BASE}/fields?source=custom
      200 -> {"fields": [{"id": "contact.<hex>", "label": ..., "type": ..., "modality": ..., "source": ...}]}
      NOTE the wrapper key is "fields", NOT "typed_custom_fields". No pagination.
  POST  {APOLLO_BASE}/fields
      body: {"label": "AI Opening Line", "modality": "contact", "type": "string", "meta": {"max_length": 500}}
      200 -> {"typed_custom_fields": [{"id": "<hex>", ...}]}       # RAW hex, no prefix
  PATCH {APOLLO_BASE}/contacts/{contact_id}
      body: {"typed_custom_fields": {"<raw hex field id>": "<opening line>"}}

THE GOTCHA (HIGH confidence, cross-verified across 4 Apollo doc pages — 04-RESEARCH.md §1):
  GET /fields returns each field's id PREFIXED by modality ("contact.<hex>").
  Every write path (bulk_create's and PATCH's typed_custom_fields dict) expects the RAW UNPREFIXED hex.
  Passing the prefixed form silently fails to attach anything — Apollo ignores the unrecognized key
  rather than erroring. Always: raw_field_id = field["id"].split(".", 1)[-1]
