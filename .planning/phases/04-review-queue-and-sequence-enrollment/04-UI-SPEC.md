# Phase 4 — UI Design Contract

> Visual and interaction contract for the new Review Queue page. Generated by gsd-ui-researcher, verified by gsd-ui-checker. This document **extends `01-UI-SPEC.md`, `02-UI-SPEC.md`, and `03-UI-SPEC.md`** — all color/spacing/typography tokens are inherited unchanged; only new elements introduced by this phase (path-scoped template editor, manual-row review table, checkbox/badge state swap, confirmation dialog) are specified below. Do not introduce new tokens that contradict the prior baseline. Streamlit is not React/Next.js/Vite — **the shadcn gate does not apply** (same as Phases 2 and 3).

## Spacing Scale

Inherited unchanged from `01-UI-SPEC.md` (multiples of 4, achieved via Streamlit's native layout primitives — no custom CSS injection anywhere in this codebase, confirmed by grep in Phase 3's research):

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Gap between a status badge icon and its label |
| sm | 8px | Gap between the "Approve Selected" and "Approve All" buttons when placed side by side (`st.columns(gap="small")`) |
| md | 16px | Default gap between stacked page sections (native Streamlit block rhythm) |
| lg | 24px | Internal padding within the template editor's validation warning block |
| xl | 32px | Gap between major page sections: page header → path selector → template editor → queue table → approve action row |
| 2xl | 48px | Space above `st.title("Review Queue")` |
| 3xl | 64px | Reserved, not used on this page |

Exceptions:
- `st.text_area` for the template body uses an explicit `height=240` (px) parameter — this is a content-area sizing value, not a layout-spacing token, and is exempt from the 8-point rule (matches Streamlit's own API, which takes raw pixel heights for this one widget).
- One `st.divider()` is inserted between the template editor and the queue table (mirrors Phase 3's divider between the results table and the "Email Drafts" section) — visually separates "editing the shared template" from "reviewing individual contacts."
- Touch targets: "Save Template", "Approve Selected", and "Approve All" buttons must not be shrunk below Streamlit's default control height (~40px); treat 44px as the floor, same as Phases 1–2.

## Typography

Inherited unchanged from `01-UI-SPEC.md` / `02-UI-SPEC.md`:

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 16px | 400 (regular) | 1.5 |
| Label / Caption | 14px | 400 (regular) | 1.5 |
| Heading | 20px | 600 (semibold) | 1.2 |
| Display | 32px | 600 (semibold) | 1.2 |
| Draft preview (monospace) | 14px | 400 | 1.5 |

Mapping to this phase's new components:
- Display (32px/600) → `st.title("Review Queue")` — the single page title.
- Heading (20px/600) → `st.subheader("Email Template — {Path}", icon=":material/edit_note:")` and `st.subheader("Drafts Awaiting Review — {Path}", icon=":material/fact_check:")` — the two named sub-sections on this page.
- Body (16px/400) → path selector value, template subject/body field text, per-row Name/Company/Title cells, count captions.
- Label/Caption (14px/400) → field labels, helper captions under the template editor, badge label text (`st.badge` renders at caption scale by default — no override needed).
- Draft preview (14px/400, monospace) → `st.code(full_text, language=None)` inside each "View draft" expander — identical to Phase 3's pattern, reused verbatim per D-10.

Only two weights used (400, 600) — no change from the established `headingFontWeights = 600` override.

## Color

Inherited unchanged from `01-UI-SPEC.md` / `02-UI-SPEC.md`:

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | #FFFFFF | Page background, main content area |
| Secondary (30%) | #F0F2F6 | `st.container(border=True)`-style chrome on the template editor block; `st.expander`/`st.code` background (Streamlit-managed) |
| Accent (10%) | #2563EB | Reserved exclusively for: the "Save Template" button, the "Approve All" button, and the `st.dialog`'s "Confirm" button (all `type="primary"`) |
| Destructive | #DC2626 | Not used this phase. See rationale below — the irreversible-send risk (D-09) is mitigated via the confirmation dialog gate, not via red button styling. |

Accent reserved for: **"Save Template"** (commits an edited shared template — D-03/D-06), **"Approve All"** (the headline bulk-enrollment action — ROADMAP success criterion 2), and the confirmation dialog's **"Confirm"** button (the actual irreversible trigger). "Approve Selected" is intentionally **not** accent-colored (`type="secondary"`, default styling) — both buttons perform the same class of action per QUEUE-03, but Streamlit's own convention (already used across Phases 1–2 for sequential-but-distinct CTAs) reserves the accent for one headline action per interaction group to avoid diluting the 10% accent budget; "Approve All" is the more common path (matches the roadmap's own framing: "a single 'Approve All' button") so it carries the accent. Do not apply accent to the path selector, template subject/text-area fields, or the per-row checkboxes — those remain neutral/default-styled Streamlit widgets.

**On the Destructive token (#DC2626) — deliberately not introduced this phase:** Phase 2's UI-SPEC flagged "the first true destructive action (bulk sequence enrollment) remains Phase 4." Having now designed this phase's flow, the decision is: enrollment is *irreversible* (real emails send) but is not a *destructive-delete* in the traditional red-button sense — nothing is removed or lost, and D-09's confirmation dialog is the safety mechanism, not a red warning color. Using `type="primary"` (accent blue) for the dialog's Confirm button, exactly as RESEARCH.md's Pattern 3 code example shows, keeps the interaction consistent with every other "commit" action in this app. The destructive-red token remains reserved for a future genuinely destructive action (e.g., a delete/undo operation), none of which exist in v1.

**Status/semantic colors** — extends the Phase 1–3 system with `st.badge`'s native color palette for this phase's new per-contact outcome states:

| State | Color | Streamlit primitive | Used for |
|-------|-------|----------------------|----------|
| Enrolled (success) | green | `st.badge("Enrolled", icon=":material/check_circle:", color="green")` | Replaces a row's checkbox after Apollo confirms enrollment in its response body (D-07, D-12) |
| Skipped (non-blocking, retryable) | orange | `st.badge("Skipped — {reason}", icon=":material/error:", color="orange")` | Rendered alongside (not replacing) a row's checkbox — the contact stays `status='drafted'` and selectable for retry (D-08) |
| Empty queue (zero drafts, not a failure) | neutral | `st.info` | Zero drafted contacts for the selected path — no error, nothing went wrong |
| Batch-call failure (network/401/403/429) | red | `st.error`, icon `:material/cancel:` | The contact-creation or sequence-enrollment API call itself failed outright (not a per-contact skip) — see Copywriting Contract |
| Validation failure (template save) | Streamlit default warning yellow | `st.warning`, icon `:material/error:` | Merge-field validation blocks a template save (D-06) |

## Layout & Review Queue Flow State System

This is the core interaction contract for Phase 4 — the executor should treat this table as authoritative. Page order, top to bottom:

1. `st.title("Review Queue")` + `st.caption` framing sentence.
2. Path selector (D-11): `st.selectbox`, same three options/order as Phase 2's path picker for visual and mental-model consistency: "Club Sponsorship", "Productthon Sponsorship", "Client Sourcing" (reuses `discovery/logic.py`'s `PATH_OPTIONS` list — do not re-derive a new label set). No placeholder/`index=None` here — unlike Discovery's optional-until-chosen picker, this page always has a meaningful default (first path alphabetically or the path with the most drafted contacts — planner's choice, not a design contract concern) since there is no "do nothing" state for this page.
3. `st.divider()`.
4. **Template editor section** (D-03) — see dedicated contract below.
5. `st.divider()`.
6. **Queue section** (D-10, D-11, D-12) — see dedicated contract below.
7. **Approve action row** (D-09) — see dedicated contract below.

| Stage | State | Trigger / Condition | Blocking Behavior | Visual Treatment |
|-------|-------|----------------------|--------------------|--------------------|
| Page load | Queue populated | ≥1 prospect at `status='drafted'` for the selected path | None | Table renders per D-10/D-12 below |
| Page load | Empty queue | 0 prospects at `status='drafted'` for the selected path | "Approve Selected"/"Approve All" buttons are not rendered at all (nothing to approve) | `st.info`, icon `:material/inbox:`, copy per Copywriting Contract — never `st.warning`/`st.error` |
| Path switch | Selector changed | Teammate picks a different path from the selector | Template editor and queue table both re-render for the newly selected path; any unsaved template edits in the previous path's text area are discarded (no cross-path draft state) | Full section re-render, same as Discovery page's pattern of re-running fresh on input change |
| Template save | Validating | "Save Template" clicked | Save is blocked; text area remains editable | If invalid: `st.warning` inline, per Copywriting Contract (D-06) |
| Template save | Success | All 3 merge fields present, save completes | Every currently visible drafted-contact row's preview re-assembles immediately with the new template (D-04) — no stale previews | `st.success` one-line confirmation directly below the "Save Template" button |
| Approve | Loading (stage 1) | "Confirm" clicked in dialog | Dialog closes; page shows in-progress state, buttons disabled/hidden during the call | `st.spinner("Creating Apollo contacts...")` |
| Approve | Loading (stage 2) | Contact creation succeeded, enrollment call in flight | Same as above | `st.spinner("Enrolling contacts in the {Path} sequence...")` |
| Approve | Per-contact mixed outcome | `add_contact_ids` response returns some Enrolled, some Skipped (D-07/D-08) | Batch does not block on partial failure; page reruns with updated per-row state | Enrolled rows: checkbox replaced with green `st.badge` (D-12). Skipped rows: checkbox remains (still selectable for retry) + orange `st.badge` with Apollo's stated reason appended inline |
| Approve | Batch call hard failure | Contact-creation or enrollment API call itself fails (network/401/403/429 — not a per-contact skip) | No rows change status; entire selected batch remains `status='drafted'`, fully retryable | `st.error`, icon `:material/cancel:`, exact copy per Copywriting Contract |
| Approve | Confirmation gate | "Approve Selected" or "Approve All" clicked, before any API call fires | Nothing changes on the page yet — waiting on dialog response | `st.dialog("Confirm enrollment")` per D-09, small width (Streamlit default), exact copy per Copywriting Contract |
| Approve | Cancelled | "Cancel" clicked in dialog | No API call fires, dialog closes, queue unchanged | Dialog dismisses, page reruns to the pre-dialog state |

Icon assignments (extends the Phase 1–3 Material Symbols table):
- Template editor section header → `:material/edit_note:`
- Queue section header → `:material/fact_check:`
- Empty queue (not a failure) → `:material/inbox:`
- Enrolled (success) → `:material/check_circle:` (same as Phases 1–3's Pass/Success icon)
- Skipped (non-blocking retry) → `:material/error:` (same icon family Phase 3 used for its warning banner — signals "needs attention," not "hard failure")
- Batch hard failure → `:material/cancel:` (same as Phases 1–3's hard-block icon)
- Draft preview expander → `:material/mail:` (reused verbatim from Phase 3's exact pattern, D-10)
- Approve action → `:material/send:` on both "Approve Selected" and "Approve All" buttons

## Template Editor Contract (D-03–D-06)

| Property | Value |
|----------|-------|
| Placement | Above the queue list, below the path selector (D-03) — never on the Discovery page's read-only "Email Drafts" section |
| Subject field | `st.text_input("Email subject", value=<current subject for path>)` |
| Body field | `st.text_area("Email body", value=<current body for path>, height=240)` |
| Helper caption (shown under the body field) | Exact required-fields reminder, see Copywriting Contract |
| Save action | `st.button("Save Template", type="primary", icon=":material/save:")` |
| Validation (D-06) | Runs on click, before any write: all three of `{first_name}`, `{company}`, `{opening_line}` must be present and correctly spelled in the combined subject+body text. Missing/broken → block save, show `st.warning` inline (does not clear the teammate's edits), do not touch `template_override` |
| On successful save | Persist to `template_override` (survives restarts, D-05); immediately re-assemble every visible drafted contact's preview for the current path with the new text + their existing AI opening line (D-04) — the queue table below reflects the new copy without a page reload |
| Reset behavior | No "Reset to default" control specified this phase — out of scope unless the planner determines it's trivial; not a locked requirement |

## Queue Table Contract (D-10, D-11, D-12)

| Property | Value |
|----------|-------|
| Component | Manual `st.columns` row loop, **not** literal `st.dataframe` — visually approximates a table (D-10's intent) while supporting the per-row expander and dynamic checkbox↔badge swap that a native dataframe cannot (see 04-RESEARCH.md "Alternatives Considered" for the full rationale) |
| Header row | One `st.columns` row with bold `st.markdown` labels: **Select**, **Name**, **Company**, **Title**, **Status** — rendered once above the per-contact rows |
| Row columns, exact order | Select (checkbox or badge) — Name — Company — Title — Status (blank until an approve action runs) |
| Row source | All prospects at `status='drafted'` for the currently selected path — no pagination this phase (matches the existing ≤50-per-batch cap from Phase 2, DISC scope) |
| Checkbox default | Checked (QUEUE-03) — every row starts selected; teammate unchecks to exclude a specific contact from the next Approve action |
| Draft preview | One `st.expander("View draft — {Name} ({Company})", icon=":material/mail:", expanded=False)` per row, placed directly below that row's column strip, containing `st.code(full_text, language=None)` where `full_text = f"Subject: {subject}\n\n{body}"` — identical pattern to Phase 3's `discovery_page.py` implementation, reused verbatim per D-10 |
| Row order | Same order the queue query returns (no custom sort control this phase) |
| Post-approval state (D-12) | Enrolled row: Select column becomes `st.badge("Enrolled", color="green", icon=":material/check_circle:")` in place of the checkbox, for the remainder of the current run (row naturally drops from the query on next reload since it's no longer `status='drafted'`). Skipped row: checkbox remains interactive (still retryable), Status column shows `st.badge("Skipped", color="orange", icon=":material/error:", help="<Apollo's stated reason>")` with the reason also inline in the badge label text (not tooltip-only, for accessibility) |

## Approve Action & Confirmation Contract (D-07, D-08, D-09)

| Property | Value |
|----------|-------|
| Buttons | `st.button("Approve Selected", type="secondary", icon=":material/send:")` and `st.button("Approve All", type="primary", icon=":material/send:")`, placed side by side via `st.columns(2, gap="small")` below the queue table. Both hidden entirely when the queue is empty. |
| Selected count | Both buttons' labels should reflect a live count where practical, e.g. "Approve Selected (N)" / "Approve All (M)" — exact counts sourced from checkbox state / total drafted rows |
| Confirmation gate (D-09) | `st.dialog("Confirm enrollment")` fires before any API call, for **both** buttons — no immediate-fire exception (this is a deliberate departure from Discovery's immediate-fire Find/Enrich buttons, justified by irreversibility) |
| Dialog copy | `"Enroll {N} contact{s} into the {Path Label} sequence?"` — exact wording locked by D-09 |
| Dialog buttons | `st.columns(2)`: "Confirm" (`type="primary"`, fires the approval, then `st.rerun()`) and "Cancel" (`type="secondary"`, dismisses with no side effects, then `st.rerun()`) |
| Confirmed outcome (D-07) | Only contact IDs present in Apollo's `add_contact_ids` response `contacts[]` array are marked Enrolled. Every other submitted contact is marked Skipped with Apollo's stated reason — an HTTP 200 alone is never sufficient |
| Partial failure (D-08) | Does not block the rest of the batch; every contact's actual per-row outcome renders after the call completes, per the Queue Table Contract above |
